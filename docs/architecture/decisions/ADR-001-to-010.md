# Architecture Decision Records (ADR-001 through ADR-010)

This document formalizes the ten foundational architecture decisions for Devnagari PG & Hostel.

---

### ADR-001: Monorepo for Frontend & Backend
* **Status:** Approved
* **Decision:** House React (TypeScript) frontend in `apps/web` and Java (Spring Boot) backend in `apps/api` within a single monorepo.
* **Rationale:** Keeps API contracts, schema migrations, and frontend clients synchronized in a single review workflow.

---

### ADR-002: Modular Monolith Architecture
* **Status:** Approved
* **Decision:** Build as a single deployable Spring Boot application structured with strict domain package boundaries (`com.devnagari.pg.<domain>`).
* **Rationale:** Microservices add unneeded operational overhead (distributed transactions, network latency, deployment complexity) at this scale.

---

### ADR-003: PostgreSQL with Versioned Flyway Migrations
* **Status:** Approved
* **Decision:** Use PostgreSQL as the relational database, managed via Flyway versioned SQL scripts. Hibernate `ddl-auto` is set to `validate`.
* **Rationale:** Provides deterministic, repeatable migrations across local and production environments.

---

### ADR-004: OpenAPI Canonical Contract First
* **Status:** Approved
* **Decision:** Maintain `contracts/openapi.yaml` as the canonical API contract.
* **Rationale:** Eliminates API drift between Spring Boot controllers and frontend client services.

---

### ADR-005: Server-Enforced Branch-Scoped Authorization
* **Status:** Approved
* **Decision:** Enforce branch authorization boundaries at the Spring Security and database query layer.
* **Rationale:** Client-side branch filtering in React is for user experience only, never security.

---

### ADR-006: Explicit Domain Ownership & Package Boundaries
* **Status:** Approved
* **Decision:** Separate concerns into distinct domains (Accommodation, Residents, Inquiries, Billing, Payments, Housekeeping, Complaints, Reports).
* **Rationale:** Prevents tight coupling. E.g., a Resident is distinct from a BedAllocation; a Bill is distinct from a Payment.

---

### ADR-007: Single Source of Truth for Documentation
* **Status:** Approved
* **Decision:** Generated documentation and manually maintained documentation must never compete.
* **Rationale:** Avoids conflicting drift between code, OpenAPI specifications, and markdown documentation.

---

### ADR-008: Shared AGENTS.md and Reusable Markdown Skills
* **Status:** Approved
* **Decision:** Maintain an agent-agnostic operating standard in `AGENTS.md` and standard skills in `agent/skills/`.
* **Rationale:** Enables any coding agent (Claude Code, Antigravity, Cursor) to follow the identical engineering workflow.

---

### ADR-009: Strict Financial Reconciliation & Monetary Precision
* **Status:** Approved
* **Decision:** Use `BigDecimal` in Java and `NUMERIC(12,2)` in PostgreSQL. Enforce double-entry style balancing between invoices, payments, and allocations.
* **Rationale:** Floating point types lead to cumulative rounding errors. Financial integrity requires full auditability.

---

### ADR-010: Concurrency-Safe Bed Allocation Constraints
* **Status:** Approved
* **Decision:** Enforce non-overlapping bed allocations at the database level using PostgreSQL exclusion constraints (`EXCLUDE USING gist`) and pessimistic write locking in Spring Boot services.
* **Rationale:** UI button disabling cannot guarantee race-free bed assignment when multiple staff members check in residents simultaneously.
